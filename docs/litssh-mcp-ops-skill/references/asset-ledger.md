# 运维资产档案（OPS_ASSETS.md）维护细则

> 本文件是 `SKILL.md` 第 9 节的展开，**按需查阅**。
> 目标：让资产/拓扑知识“自动进化”——在工作区维护一份独立的资产 + 应用拓扑关系文档，每次用 MCP 排障/运维时先读它、再用最新事实更新纠正它，从而越来越准地定位**服务器、应用、日志**。
> 起手模板见同目录 `../OPS_ASSETS.template.md`（另存为工作区的 `OPS_ASSETS.md`）。

## 位置与命名
- 默认在工作空间根目录建 **`OPS_ASSETS.md`**；若工作区已有文档目录约定（如 `docs/`）可放那里；用户指定位置时以其为准。
- 只维护**一个**权威文件，避免多处副本互相矛盾。
- 用你自己的文件读写能力维护（MCP 没有写文件工具；`ssh_*` 只作用于远端）。

## 何时做（这是“进化”的关键）
- **每次运维任务开始时**：档案存在 → 先读，用它拿准确 `serverId/appId/datasourceId`、端口、日志/部署路径、依赖；不存在 → 询问用户是否创建，默认创建。
- **任务过程中/结束时**：一旦发现**新事实**或**纠正了旧事实**（新服务器/应用、真实日志路径、端口、依赖、隧道跳板、被禁用项、废弃/示例配置），**立即更新档案**并追加一条变更记录。
- 拓扑有变动、或用户要求时：调 `topology_discover` 与档案**对账**，把新增/未匹配端点写入“待确认”。

## 内容结构（建议，用表格保持精简可机读）
- **服务器**：`id` | 名称 | `host:port` | 环境(prod/test) | 用途 | 登录方式 | 提权(sudo/su/自动) | 状态(启用/禁用) | 备注
- **数据源**：`id` | 名称 | 类型 | 入口 `host:port` | 访问方式(直连 / SSH隧道 + 跳板服务器) | 归属服务器 | 备注
- **应用**：`id/名称` | 所属服务器 | 端口 | 部署路径(jar/workdir) | **日志路径** | 配置文件 | 启动方式(自建/systemd/docker) | 备注
- **拓扑关系**：源 | 关系(`runsOn`/`connectsTo`/`canAccess`/`relatedTo`) | 目标 | 证据
- **待确认 / 存疑**：未能匹配的端点、疑似废弃或示例配置、相互冲突项（附证据）
- **更新日志**：日期 | 类型(数据/结构) | 变更 | 证据来源(工具名/命令) | 置信度(高/中/低)

## 维护规则（防止越用越乱）
1. **以 MCP 实时数据为准**：`ssh_list_servers` / `datasource_list` / `topology_get_overview` 与档案冲突时，用实时数据纠正档案并记一条变更。
2. **记稳定的 `id`**：`serverId`/`datasourceId`/`appId` 是调用工具的关键；档案里必须存 `id`，而不仅是名称/主机名（名称可能重名触发 `*_ambiguous`）。
3. **只记事实、带证据**：每条尽量标注来源工具与时间；推断类放“待确认”并降置信度。
4. **绝不存密钥**：不放密码/私钥/口令/token；用户粘贴了也要脱敏后再记。
5. **合并去重**：同一资产只留一行，变化时**改该行**而不是新增一行。
6. **冲突不硬猜**：拿不准就在“待确认”里列出并向用户确认，不要凭空写死。
7. **不覆盖用户手写内容**：用户维护的部分保留，仅追加/更新对应条目。
8. **可调整结构/内容，但必须注明原因**：允许按实际环境增删字段、表格或小节（见下节），但**每次结构性调整都要记清原因与依据**。

## 结构与内容的适应性调整（允许，但必须注明原因）

本档案允许“自行进化”，包括**结构**而不仅是数据：

- **何时可调结构**：现有字段/表格无法表达实际环境时（例如需要记录：域名/证书到期、Cron/定时任务、消息队列、备份任务、K8s 命名空间、环境隔离矩阵、值班/负责人等）。**有共性、可复用**才固化进结构；一次性特例先记在“待确认 / 备注”，不要动结构。
- **怎么注明原因**：在“更新日志”里加一条 `类型=结构` 的记录，写清三点：**改了什么**（增/删/改了哪个表或字段）、**为什么**（触发场景 + 证据/工具输出）、**影响**（是否影响已有条目、是否向后兼容）。
- **守则**：
  1. **向后兼容**：已有条目尽量保留；非必要不删列、不删数据。
  2. **不频繁重构**：先观察是否普遍，再固化进结构。
  3. 结构变更同样适用“**不含密钥**、**冲突不硬猜**、**不覆盖用户手写内容**”。
  4. **大改前先向用户确认**（结构变动影响可读性与他人使用）。

## 文档过大时的拆分（允许，同样需注明原因）

当单个 `OPS_ASSETS.md` 变得过长、难以检索时，可按需**拆分**成“主索引 + 子文件”。

- **何时拆**：正文明显变大或逐条翻找变慢时（经验阈值：正文 > ~300 行，或“更新日志”> ~100 条，或应用/服务器条目 > ~30 个）。
- **怎么拆**（示例布局，放在与 `OPS_ASSETS.md` 同目录）：
  - `OPS_ASSETS.md` —— **主索引/总览**：摘要 + 各区块标题下的**链接**；
  - `ops/asset-servers.md`、`ops/asset-datasources.md`、`ops/asset-apps.md`、`ops/asset-topology.md` —— 各明细表；
  - `ops/asset-changelog.md` —— **更新日志单独成文件**（最常增长、最该先拆）。
- **守则**：
  1. **单一来源**：同一条事实只存在于一个文件，禁止两处副本。
  2. **主文档常驻入口**：`OPS_ASSETS.md` 始终是入口，含摘要与指向各子文件的相对链接；顺着链接能找到全部内容。
  3. **拆分也是结构变更**：在更新日志以 `类型=结构` 记明：拆了哪些、为什么、新布局（路径）。
  4. **不预先过度拆分**：只有确实变大才拆；小文档保持单文件。
  5. 链接用**相对路径**（随工作区移动不失效）；拆分前先与用户确认（影响可读性）。

## 与 MCP 工具配合
- 刷新清单：`ssh_list_servers`、`datasource_list`、`topology_get_overview`、`topology_get_dependencies`。
- **整机盘点**：`ssh_snapshot_get(serverId)` 一次拿到 资源/端口↔进程↔服务（含程序路径 `exe` 与启动命令 `cmdline`）/Docker 容器/nginx 域名与证书/systemd/**安全巡检（security）**，快速补全“端口/进程/容器/证书/服务归属”，并作为安全基线证据；需要最新数据用 `ssh_snapshot_refresh`。
- 补全应用细节：`java_processes`（启动命令/jar/工作目录）、`docker_ps`/`docker_inspect`（端口/挂载）、`log_find`（日志路径）、`service_status`（systemd 单元）。
- 对账发现：`topology_discover`；把 `UnmatchedEndpoints`/notes 里的“未匹配端点、占位符主机、疑似外部依赖”写进“待确认”。
- 提速回顾：档案里存好每个应用的**日志路径**后，后续直接 `log_tail(serverId, appId=...)` / `log_grep`，无需再 `log_find`。
