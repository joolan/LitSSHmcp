# CI/CD 发布失败快速回滚 runbook（按需读取）

适用：流水线发布失败/发布后异常，需要在分钟级决定并执行回滚。回滚 = 变更操作：先只读取证，最小变更，变更后验证。

## 0. 决策门槛（先回答再动手）
1. 影响面：核心链路不可用/数据风险 → 立即回滚；仅非关键告警 → 可观察修复。
2. 可回滚性：上一版本产物/镜像 tag 是否可得；数据库迁移是否已执行（有向下迁移才能回）。
3. 是否有人工批量任务进行中（发布前检查单项）。

## 1. 取证（只读，5 分钟内完成）
1. 记录现场：当前版本号/镜像 tag、发布时间、流水线失败点。
2. 状态：`service_status` 或 `docker_ps`（重启次数、退出码）。
3. 日志：`service_logs`/`docker_logs`/`log_tail` 抓启动后首个异常栈与启动失败原因。
4. 健康：`curl -sS -m 8 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<port>/health`；端口 `ssh_snapshot_get section="portmap"`。
5. 依赖：`app_health_snapshot(appId)` 排除「回滚也救不了」的外部依赖故障（数据库/上游挂了，回滚无效）。

## 2. 选择回滚方式（按发布形态）
| 发布形态 | 回滚动作 | 要点 |
|---|---|---|
| systemd + 二进制/脚本 | 切回上一版本产物目录/软链 → `systemctl restart <unit>` | 确认产物仓库有上一版；保持配置兼容 |
| 容器/镜像 | `docker stop/rm` 后用上一 tag 重新起（或 compose 指回旧 image） | 记下当前 tag 便于再次发布；注意数据卷不回滚 |
| 配置发布 | 恢复上一份配置文件 → `nginx -s reload`/服务 reload | 配置与版本配套时两者一起回 |
| 数据库有迁移 | 先确认有向下迁移脚本；无则止步，升级处理 | 不可逆迁移禁止盲目回滚应用 |

## 3. 执行（审批与最小变更）
1. 向用户说明：回滚目标版本、影响范围、预计中断、回滚点（当前版本 tag/备份路径），经明确要求 + 审批后执行。
2. 执行 restart/切版本（`ssh_execute_sudo` 或 docker 命令，均会弹审批）。
3. 单点回滚成功后再扩到其余实例（灰度顺序与发布相反）。

## 4. 回滚后验证（重跑发布后验证清单）
1. 进程 Running、重启次数不再增长。
2. 健康端点 200、关键端口监听正常。
3. 启动日志无新异常；错误日志增速归零。
4. 依赖可达；核心链路冒烟（用户或业务侧确认）。

## 5. 收尾
1. 保留现场：失败版本产物/tag、异常日志片段、回滚操作记录，供事后复盘。
2. 总结写入记忆：发布标识 → 失败根因（若已知）→ 回滚方式 → 验证结果，下次同类发布自动召回。
3. 修复后重新走发布流程，勿在回滚态直接热修。

## 注意
- 回滚不回滚数据：确认本次发布是否产生新格式写入，评估兼容性。
- 涉及重启/切版本前确认无批量任务；多实例按灰度逆序回滚。
- 遵循「先只读取证 → 最小变更 → 变更后验证」，全程向用户同步关键决策点。
